承認フロー付き CDC デモの構成

設計側で承認した資材の変更が、Aurora の変更ログ（WAL）から Confluent Cloud のフルマネージドコネクタを通って調達側の取り込み待ちテーブルと S3 に届くまでの全体像。

データの流れ

  1. 1
    ブラウザ → ALB → EC2
    ALB がパスで 2 つのアプリに振り分ける。ALB はパスを書き換えないので、アプリは BASE_PATH の下で待ち受ける。
  2. 2
    設計側で承認
    申請テーブルの確定と engineering.materials の UPDATE を 1 つのトランザクションで実行する。この UPDATE が CDC の起点。
  3. 3
    WAL を CDC Source が読む
    publication と replication slot 経由で、変更後の行だけを取り出す。
  4. 4
    topic に AVRO で書き込む
    スキーマは Schema Registry が管理する。
  5. 5
    Postgres Sink が staging に INSERT
    SMT で必要な 3 列に絞り、列名を proposed_* に変えて incoming_material_changes に pending で入れる。
  6. 6
    調達側で Accept
    staging の確定と procurement.materials への UPSERT を 1 つのトランザクションで実行する。
  7. 7
    S3 Sink がアーカイブ
    同じ topic を独立に読み、10 分ごとに JSON で S3 に書き出す。

構成上のポイント

  • コネクタはすべて Confluent Cloud のフルマネージド。Aurora を公開設定にし、SG で Confluent の Egress IP だけに 5432 番を開けている。
  • S3 Sink は IAM Role（Provider Integration）で書き込む。組織の規約でアクセスキーの新規作成が制限されているため。
  • ALB・S3・IAM Role は Aurora の SG ルールと Terraform の state を分けている。ALB だけ destroy しても CDC の経路は残る。
  • ALB は起動中ずっと時間課金される。後片付けは「コネクタ削除 → slot と publication 削除 → destroy」の順。
